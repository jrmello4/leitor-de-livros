# Issues 18–24 Review Follow-ups Design

## Scope and delivery base

Implement GitHub issues #18 through #24 on one integration branch based on `origin/main` after PR #17. The branch also carries the previously unmerged implementations of issues #7 through #12, replayed in their original order, because the release and performance harnesses depend on those reader features.

The work fixes evidence correctness and removes the specific maintainability problems found in review. It does not publish a release, add a new renderer, change performance thresholds, or redesign the reader interface.

## Shared Windows installed-app harness (#18)

Create a focused script module that owns the Windows lifecycle shared by installer smoke and performance validation:

- recursive artifact discovery and installer/executable selection;
- isolated installation and temporary run directories;
- allocation of an available ephemeral CDP port;
- application launch with WebView2 remote debugging;
- condition-based polling with explicit deadlines;
- termination of the owned process tree; and
- idempotent cleanup restricted to the owned run directory.

The module accepts injected filesystem, process, clock, networking, and launch dependencies at its test seam. Production callers use real defaults. Installer smoke retains fixture integrity, removal, restart, missing-PDFium, and evidence serialization. Performance validation retains scenario measurement, memory sampling, cache inspection, and report generation. Neither caller duplicates lifecycle mechanics.

Lifecycle failures carry a stage (`discovery`, `installation`, `launch`, `connection`, `execution`, or `cleanup`) and an actionable message. Cleanup failures may enrich the primary failure but must not hide it or target paths outside the owned run root.

## Performance evidence correctness (#19)

Add one supported page-transition waiter that reads the committed page index and polls until it equals the expected index or the shared deadline expires. All reset, 50-page navigation, rapid switching, and long-session paths use this waiter; scripts never call assertion matchers directly on a Playwright `Locator`.

First-frame measurement starts immediately before the import action. It ends only after import completion, reader readiness, and two browser animation frames. Import duration remains a separate metric measured from the same start point to import completion. The first-frame threshold and report use the complete action-to-frame interval.

Tests exercise the navigation waiter with observable page changes and timeout, then exercise timing with an injected monotonic clock. They must fail for the previous unsupported locator call and for a timer reset after import completion.

## Installer lifecycle evidence (#20)

Use the shared harness dependency seam to test lifecycle behavior without performing a real install. Tests cover selection of an unused CDP port, rejection of occupied candidates, connection timeout, owned process-tree termination, idempotent cleanup, and structured failure evidence.

Every destructive test operation receives an explicit temporary run root and verifies its resolved target is contained by that root. Missing processes or files during cleanup count as already cleaned. Result serialization preserves run identity, lifecycle stage, primary error, and any cleanup diagnostic.

## Visual acceptance gates (#21)

The visual matrix requires the reader's current-page element to be visible and to expose a valid committed page index. A visible but empty or invalid marker fails before capture.

RTL scenarios perform a real tactile page transition. The test records the turning sheet's horizontal transform or equivalent direction signal during the transition, verifies that it moves in the RTL direction, and then verifies the committed destination. The assertion runs for desktop and narrow viewports. Optional GPU backends may be skipped only with a backend-specific reason; static evidence remains mandatory.

Existing clipping, empty-region, control-overlap, boundary, cancellation, reduced-motion, fullscreen, single-page, spread, LTR, and backend checks remain intact.

## Native import lifecycle ownership (#22)

Split native import into two responsibilities:

- picker functions obtain file or folder paths and translate picker failure/cancellation into an explicit outcome;
- one import operation owns `isImporting`, diagnostics, announcements, import execution, library refresh, metadata hydration, cache refresh, and opening the imported publication.

Direct-path automation calls the same import operation. The operation enters loading once and clears it in one `finally` path. Cancellation produces the cancellation announcement without an error diagnostic. Picker and importer exceptions use the same localized failure state. Browser-only import remains unchanged.

Component-level tests cover picker cancellation, picker failure, importer failure, empty results, successful import, and direct-path import.

## Typed smoke phases (#23)

Replace the smoke harness status string with a discriminated state using the closed phases `ready`, `importing`, `imported`, and `failed`. The failed state carries a reason of `missing-path` or `import`. A pure mapping derives visible copy from the state, while submission guards and button disabled state depend only on `phase === 'importing'`.

Empty input transitions to `failed/missing-path` without invoking import. A successful request transitions `ready → importing → imported`; a rejected request transitions `ready → importing → failed/import`. Tests use alternate copy to prove behavioral state does not depend on displayed text.

## Renderer backend policy (#24)

Keep `parseVisualBackend` as the single policy for interpreting the query string and build guard. Reader code calls it directly; the pass-through backend-selection function and its duplicate test matrix are removed.

The authoritative tests cover `auto`, `webgpu`, `webgl2`, `static`, invalid values, and the production-build guard. Visual evidence continues recording requested backend, actual backend, and explicit skip reason.

## Sequencing and commits

Implement #18 first. Issues #19 and #20 are blocked by its shared lifecycle seam and follow in that order. Issues #21, #22, #23, and #24 are independent after the baseline is green. Each issue receives its own red-green test cycle and commit so review can accept or revert it independently.

## Verification

Focused checks run after every red-green cycle. The final gate runs:

- all Vitest tests and the TypeScript/Vite production build;
- release-script lifecycle tests and performance-contract tests;
- Playwright visual tests that are available in the local environment, with backend skips reported explicitly;
- Rust formatting, Clippy with warnings denied, and all native tests; and
- a two-axis code review against issues #18–#24 and repository standards.

The Windows installer smoke and reference-hardware performance jobs remain environment-dependent evidence runs. Their deterministic lifecycle and contract seams are exercised locally; the actual installer and GPU artifacts are produced by their existing Windows CI/manual workflows.
